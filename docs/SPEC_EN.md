# Rack Inventory Studio — Project and Data Format Specification v0.1

## 1. Project character

**Rack Inventory Studio** is an offline-first desktop application for documenting physical device placement in rack cabinets.

The project is intended as a simple descriptive system for documenting what is located in specific racks, on specific rack units, on the front or rear side.

It is not a full DCIM, CMDB, or IPAM system.

## 2. Main project decisions

| Area | Decision |
|---|---|
| Name | Rack Inventory Studio |
| License | MIT |
| Application type | Desktop, offline-first |
| Data source | Shared organizational Git repository |
| Local work | Local repository clone |
| Data format | YAML |
| Model | Asset-first |
| RacksDB | Inspiration / possible future import-export, not canonical model |
| NetBox / Nautobot / Zabbix / CMDB API | Outside MVP |
| Physical audit | Outside MVP |

## 3. MVP scope

MVP includes:

- locations,
- racks,
- device models,
- device instances,
- rack objects as special models,
- placements in racks,
- one rack side visible at a time,
- unplaced devices panel,
- rack objects panel,
- device import from CSV,
- repository validation,
- simple Git workflow,
- conflict branch for Git conflicts.

Outside MVP:

- full CMDB,
- IPAM,
- cabling,
- power,
- vertical PDUs,
- half-width devices,
- physical audit,
- NetBox/Nautobot/Zabbix integrations,
- merge request workflow,
- automatic Git conflict resolution.

## 4. Model philosophy

The project is **asset-first**.

The most important concept is a concrete device instance and its physical placement:

```text
Device
  -> Placement
    -> Rack
      -> Location
```

The system does not store CPU, RAM, disks, or detailed hardware parameters. Such information should live in an external CMDB or another source system.

## 5. Repository structure

Accepted structure:

```text
inventory/
  repo.yaml

  locations.yaml

  racks/
    warsaw-serverroom-a.yaml
    krakow-serverroom-a.yaml

  device-models/
    servers.yaml
    network.yaml
    storage.yaml
    ups.yaml
    appliances.yaml
    rack-objects.yaml
    other.yaml

  devices/
    servers.yaml
    network.yaml
    storage.yaml
    ups.yaml
    appliances.yaml
    other.yaml

  placements/
    rack-a01.yaml
    rack-a02.yaml
```

There is no `device-types.yaml`, because `device_type` is hardcoded in the application.

## 6. Identifiers: `id` and `code`

Every primary object has:

```text
id
code
```

### 6.1. `id`

`id`:

- is required,
- is a UUID,
- is generated by the application,
- is used for object references,
- should not change.

### 6.2. `code`

`code`:

- is required,
- is human-readable,
- is used in UI, file names, CSV import, and Git diffs,
- should be unique within the object type.

Recommended format:

```text
^[a-z0-9][a-z0-9._-]*$
```

Example:

```yaml
id: 7d73b40f-53c3-4b11-9a33-9fd5f15f72d2
code: rack-a01
name: Rack A01
```

## 7. Hardcoded `device_type`

Allowed MVP categories:

```text
server
network
storage
ups
appliance
rack_object
other
```

Meaning:

| device_type | Meaning |
|---|---|
| `server` | physical servers |
| `network` | switches, routers, firewalls, load balancers, and other network devices |
| `storage` | arrays, tape libraries, and storage devices |
| `ups` | rack UPS units |
| `appliance` | specialized appliances |
| `rack_object` | descriptive objects occupying rack space |
| `other` | other devices |

Additional classification is done through `tags`.

## 8. Model: Location

One location means one room / one server room.

File:

```text
inventory/locations.yaml
```

Example:

```yaml
locations:
  - id: 79f0b3c0-f4d3-47ad-89e1-9efae2ad5c87
    code: warsaw-serverroom-a
    name: Warsaw - Server Room A
    description: Main server room in Warsaw
    address: Warsaw, Example Street 1
    tags:
      - production
      - warsaw
```

Required:

```text
id
code
name
```

Optional:

```text
description
address
tags
```

## 9. Model: Rack

One rack file belongs to one location.

Example:

```yaml
location_id: 79f0b3c0-f4d3-47ad-89e1-9efae2ad5c87

racks:
  - id: 7d73b40f-53c3-4b11-9a33-9fd5f15f72d2
    code: rack-a01
    name: Rack A01
    height_u: 42
    row: A
    description: Rack near the entrance
    tags:
      - production
```

Required at file level:

```text
location_id
```

Required for rack:

```text
id
code
name
height_u
```

Optional:

```text
row
description
tags
```

`height_u` is required because placements must be validated against rack height.

## 10. Model: DeviceModel

`DeviceModel` describes a physical device model or a rack object model.

Example for network device:

```yaml
device_type: network

models:
  - id: 21f8ff6a-3be8-4eee-9285-df11aac1686b
    code: cisco-c9300
    name: Cisco Catalyst 9300
    vendor: Cisco
    model: Catalyst 9300
    default_height_u: 1
    tags:
      - switch
```

Example for rack object:

```yaml
device_type: rack_object

models:
  - id: 2b65592a-18b8-41c7-9a27-1f03aa631e4f
    code: blank-panel-1u
    name: Blank Panel 1U
    default_height_u: 1
    tags:
      - blank-panel
```

Required at file level:

```text
device_type
```

Required for model:

```text
id
code
name
default_height_u
```

Optional:

```text
vendor
model
description
tags
```

## 11. Model: Device

`Device` is a concrete device instance.

No `Device` instances are created for `rack_object`.

Example:

```yaml
device_type: server

devices:
  - id: 9a7c5e10-3d3a-4b31-947c-7d3cba39f314
    code: srv-db-01
    name: srv-db-01
    device_model_id: 4a7d5a62-36f4-4cd9-818e-66eac20351a1
    serial_number: ABC123456
    asset_tag: INV-00451
    external_ref: SRV-DB-01
    status: installed
    tags:
      - database
```

Required at file level:

```text
device_type
```

Required for device:

```text
id
code
status
```

Additionally, at least one of the following is required:

```text
name
serial_number
asset_tag
```

Optional:

```text
device_model_id
external_ref
description
tags
```

`device_model_id` is optional. If a device without a model is placed in a rack, the placement must explicitly define `height_u`.

## 12. Device statuses

Allowed MVP statuses:

```text
planned
in_stock
installed
to_remove
removed
disposed
unknown
```

`status` is required. The application may default to `unknown`.

## 13. Rack objects

There is no separate primary `RackObject` model.

Rack objects are represented as:

```text
DeviceModel with device_type = rack_object
```

Examples:

- blank panel 1U,
- cable organizer 1U,
- reserved space,
- unknown occupied space.

A rack object can be used multiple times in different placements.

## 14. Model: Placement

Placement links a device or rack object to a specific position in a rack.

One placement file belongs to one rack.

Example:

```yaml
rack_id: 7d73b40f-53c3-4b11-9a33-9fd5f15f72d2

placements:
  front:
    - id: 6d0dc8e6-9c87-4b9f-8d7d-2a4bb9953e22
      code: plc-srv-db-01
      target_kind: device
      target_id: 9a7c5e10-3d3a-4b31-947c-7d3cba39f314
      start_u: 12
      height_u: 2
      note: Descriptively occupies 2U

  rear:
    - id: 31580a71-1d2d-4fd8-a5c2-489b28c3f170
      code: plc-organizer-rear-01
      target_kind: device_model
      target_id: c3cb54dd-f0d8-4594-96a1-d27f59c7f3ee
      start_u: 20
```

Required at file level:

```text
rack_id
placements.front
placements.rear
```

Required for placement:

```text
id
code
target_kind
target_id
start_u
```

Optional:

```text
height_u
note
tags
```

## 15. Placement target

Allowed `target_kind` values:

```text
device
device_model
```

Rules:

- `target_kind: device` points to a concrete `Device`,
- `target_kind: device_model` can only point to a `DeviceModel` of type `rack_object`,
- a regular device model, such as a server or switch, cannot be used directly as placement target.

## 16. Height and U range

Rack units are numbered bottom-up.

Placement points to the bottom U:

```text
start_u
```

Effective height:

```text
effective_height_u =
  placement.height_u, if provided
  otherwise default_height_u from model
```

Range:

```text
end_u = start_u + effective_height_u - 1
```

Example:

```text
start_u: 12
effective_height_u: 3
range: U12-U14
```

## 17. Front / rear

Placements are split in the file into:

```yaml
placements:
  front: []
  rear: []
```

A single placement has no `side` field.

Rack view shows one side at a time:

```text
Front / Rear
```

MVP does not support changing placement side through editing.

If the user wants to move an item to the other side:

1. remove placement,
2. switch side,
3. place it again.

## 18. Collisions

Collisions are checked only within:

```text
same rack
same side: front or rear
overlapping U range
```

Front and rear are not compared.

The system does not check:

- device depth,
- physical mounting feasibility,
- half-width devices,
- vertical PDUs.

The system is descriptive, not a physical rack simulator.

## 19. Devices without placement

A Device may exist without placement.

A device is unplaced if no placement with `target_kind: device` references its `id`.

Rack view should have an:

```text
Unplaced devices
```

panel.

Removing a device from a rack removes the placement. It does not delete the device and does not automatically change its status.

## 20. Number of placements per device

In MVP:

```text
Device can have at most one active placement.
```

This does not apply to rack objects, because a `DeviceModel` of type `rack_object` can be reused many times.

## 21. Git workflow MVP

Operations:

```text
Pull latest data
Save locally
Publish changes
```

Under the hood:

```text
git pull
write YAML
validate
git commit
git push
```

Publishing to Git is blocked by validation errors of type `ERROR`.

In case of Git conflict:

- the application does not resolve the conflict,
- creates a conflict branch,
- pushes local changes to that branch,
- an administrator performs the merge in Git.

## 22. MVP views

Main views:

1. Repository / synchronization
2. Validation / problems
3. Change history
4. Device model catalog
5. Device instance catalog
6. CSV import
7. Locations
8. Location view and rack list
9. Rack view

Rack view:

- shows one side at a time,
- has Front / Rear switch,
- displays U from top to bottom on screen,
- logically numbers U bottom-up,
- has unplaced devices panel,
- has rack objects panel,
- supports drag and drop to active side.

## 23. CSV import

MVP imports only new devices.

CSV:

- uses `code`, not UUID,
- requires `device_type`,
- optionally uses `device_model_code`,
- does not update existing devices,
- duplicates are errors.

Details are defined in `VALIDATION_AND_CSV_SPEC_EN.md`.
